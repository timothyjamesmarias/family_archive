## What This Is

A family archive application for genealogical data and family history, ported
from an AdonisJS app onto the Rails template. Public pages browse artifacts
(photos, letters, documents, ledgers, audio, video) and articles; a
server-rendered family tree shows and edits the genealogy; a
server-rendered admin manages everything.

Stack: Rails 8.1, PostgreSQL, Solid Cache/Queue/Cable, Vite, Tailwind v4,
Turbo + Stimulus, Devise for auth (admin-managed users, no public signup),
Mission Control – Jobs for the queue dashboard, Action Text with the Lexxy
editor for article bodies.

## Commands

```bash
bin/setup                 # install deps, start Postgres, prepare the database
bin/dev                   # web + vite + jobs
bin/rails test            # unit + integration tests
bin/rails test:system     # system tests (headless Chrome)
npm run typecheck         # tsc --noEmit
npm run herb:lint         # Herb lint for app/views and app/components
bin/rails "family_tree:profile[all]"   # time a chart build by phase and statement
bin/rubocop               # lint
bin/ci                    # everything CI runs
docker compose up -d      # Postgres only (host port 5433)
```

Dev Postgres listens on **5433** (5432 is taken by other local projects).
Seeds create `admin@example.com` / `password` in development.

## Architecture Notes

- **Domain POROs are models.** There is no `app/services` — everything lives
  in `app/models`, organized by domain namespace (`Artifact::Uploader`,
  `Gedcom::Importer`, `Individual::Editor`, `FamilyTree::Mutations`); small
  standalone concepts stay flat (`Pagination`, `SitemapEntries`). No
  `Service` suffix, ever. Controllers validate, delegate, and shape the
  response.
- **Recursive CTEs stay as SQL strings** in
  `app/models/individual/queries.rb` and `app/models/family_tree/metadata.rb`,
  executed through Active Record. They walk parent/child edges to bounded
  depth; refactor deliberately, with the tests in `test/models` as the
  safety net.
- **Soft deletes** (`SoftDeletable` concern) apply to individuals, families,
  and family_members via a default scope; `with_deleted` escapes it. GEDCOM id
  uniqueness checks must include deleted rows — the DB unique index does.
- **`family_members` has a composite primary key** (family_id, individual_id,
  role) using Rails CPK support.
- **The family tree is server-rendered** at `/family-tree`; its whole state
  is the URL (`depth`, `up[]`, `down[]`, `edit`). `FamilyTree::Chart`
  composes `Builder#initial_tree`/`#expand_tree` (kept as they are, camelCase
  payload included) and decorates the order; `FamilyTree::Layout` positions
  people in slots (a Buchheim tidy tree over spouse blocks, plus packing);
  `FamilyTree::Edges` and `Metrics` turn that into pixels; components live
  under `FamilyTree::`. Edit mode (`?edit=1`, signed-in users) loads forms
  into a dialog frame and reuses `Individual::Editor` and
  `FamilyTree::Mutations`. Diagrams: `docs/family-tree-architecture.md`.
- **Artifact files are Active Storage attachments** — `ArtifactFile` has
  `has_one_attached :file` with a preprocessed `:thumb` variant (300px JPEG),
  so thumbnails are generated by `ActiveStorage::TransformJob` on upload.
  The `artifact_files` row carries only `file_sequence` and the annotation
  anchor. Development/test use Disk; production uses S3 (`amazon` service in
  `config/storage.yml`, configured by `AWS_*` env vars).
- **Article bodies are Action Text** (`has_rich_text :content`), edited with
  Lexxy. Records go into rich text as **embeds**: an `Embed` row (kind,
  embeddable, options) whose sgid is the `<action-text-attachment>` in the
  HTML. Lexxy drops unknown attributes from that tag, so per-embed options
  live on the row. `Embed::KINDS` is the registry — label, model, component,
  options, search — and feeds the admin's "Insert embed" dialog
  (`Admin::EmbedsController`, `embed_picker` controller); adding a kind is an
  entry there plus its component under `Embeds::`. Saving an article claims
  the embeds its body references and deletes the ones edited out. Rendering
  goes through `render_rich_text` (the app's `action_text/contents/_content`),
  which sanitizes the author's HTML *before* rendering embeds, so component
  markup isn't filtered by the author allowlist. Nothing is sanitized on save.
- **Mission Control** at `/admin/jobs` (admin-gated) shows the Solid Queue
  jobs, including Active Storage's analyze/transform/purge jobs. Development
  uses Solid Queue too (the :async default would keep the dashboard empty), so
  jobs only run under `bin/dev`, which starts the worker. Variant generation
  needs libvips (`brew install vips` locally; the Dockerfile has it).
- **GEDCOM import parses via Node** — Ruby has no maintained GEDCOM parser,
  so `Gedcom::Reader` shells out to `script/gedcom-to-json.mjs` (the same
  `read-gedcom` package the AdonisJS app used) and `Gedcom::Importer` owns all
  domain logic: upsert by GEDCOM id, replace only BIRTH/DEATH/BAPTISM/BURIAL
  events, preserve hand-added members and events. Imports run through
  `GedcomImportJob`; the admin screen shows the last result from the cache.
  `read-gedcom` is a production npm dependency and the Dockerfile keeps node
  in the runtime image for it.
- **Admin scaffolding**: `bin/rails g admin_scaffold <model> field:type …`
  generates an admin CRUD (controller + views) matching the aside-nav layout;
  add the nav link in `app/views/layouts/admin.html.erb` by hand.

## Design System

The public UI is specified by the claude.ai/design project ("Archive
Foundations" and "Archive Pages"). **The design files are the spec — follow
them literally.** Implementation glue is fine when genuinely needed to
realize the design's logic (helpers, caching, pagination windowing,
extrapolating dark mode from the ink table). What is not acceptable:
writing copy the mockups don't contain, adding features or affordances
that aren't drawn, or deviating from drawn sizes, labels, or structure
without necessity. When the design is silent, ambiguous, or impossible to
follow literally (missing backend, placeholder content), stop and ask —
the design file may get updated instead. Hex values in the design are
authoritative over its prose annotations.

Design tokens and recipe classes live in
`app/frontend/entrypoints/public.css`; ViewComponents
(`app/components`, primitives under `Ui::`) are thin maps from props to
those recipe classes so future React twins share the same vocabulary.
Previews render at `/rails/view_components` in development.

## Frontend

Two Vite entrypoint groups:

- `application.(js|css)` — the admin (Turbo + Stimulus + Tailwind slate).
- `public.(ts|css)` — public pages (Turbo + Stimulus): dark mode, mobile
  menu, annotated-photo and media controllers, and the tree's `tree-zoom`
  (pan/zoom transform) and `tree-dialog` (edit forms) controllers; Tailwind
  with the Paperwhite theme (stone/sage palette, Lora/Inter).

Every other script is a Stimulus controller one of the bundles registers;
no page loads its own entrypoint. The admin's Uppy dashboards mount through
`shared/uppy.ts`, which imports Uppy on demand so it downloads only on the
pages that use it:

- `uppy_picker` — GEDCOM import and add files: Uppy picks, the form posts
  natively (`turbo: false`) and redirects with a full page load, as before
  the controllers. A Turbo submit would keep the flash now that no reload
  meta is involved; it just hasn't been tried.
- `artifact_upload` — the artifact upload page (multi-file, "save and add
  another"; posts FormData to the JSON create).

The admin bundle also loads Lexxy and starts Active Storage direct uploads
for the rich text editor.

Both bundles run Turbo Drive. Controllers undo on disconnect what they
mount, and state a snapshot would capture is reset (the mobile menu closes
on `turbo:before-cache`, the media player resyncs from its element, flash
is `data-turbo-temporary`), so a snapshot restore comes back clean. Each
layout tracks its bundle tags (`data-turbo-track: reload`), so crossing
between admin and public is a full load. Download links carry `download`,
which Drive skips, and the public layout turns hover prefetch off
(`turbo-prefetch: false`). The tree page is an ordinary Turbo page: its
chart sits in a frame that advances the URL, and its controllers keep the
view across frame swaps and saves (values on the frame, `sessionStorage`).

The admin annotations editor (`/admin/artifacts/:id/annotations`) is the
Hotwire pattern for interactive admin pages: server-rendered markup, the
form in a Turbo Frame (`annotation_form`) so a 422 re-renders in place, and
one small Stimulus controller (`annotation_editor`) that only positions and
closes the popover. A save redirects back to the page; the controller
replays that response as a replace visit, and the page opts into morphing
with `turbo_refreshes_with method: :morph, scroll: :preserve` — per page,
not in the admin layout.

Tailwind v4 notes: dark mode is a `dark` class on `<html>` (applied and
toggled by the `dark-mode` Stimulus controller, which both layouts share —
the admin uses it too), custom classes that other classes `@apply` must be
`@utility`, and the theme lives in `@theme` inside `public.css`.

## Templates

ERB is linted by [Herb](https://herb-tools.dev) (`.herb.yml`, `npm run
herb:lint`, part of `bin/ci`). In development and test, ReActionView renders
`.html.erb` through `Herb::Engine`, so mis-nested or unclosed markup raises in
tests and shows an overlay in the browser; production stays on Erubi until
Rails 8.2 makes Herb the default.

Prefer ViewComponents over partials and view helpers for new markup —
including page-specific pieces, so a page template reads as its information
structure (`render Admin::Annotations::EditorComponent.new(file:)`). Public primitives
live under `Ui::` (recipe classes from `public.css`); admin primitives under
`Admin::` (`ButtonComponent`, `PanelComponent`, `TabsComponent`, with the
admin's slate classes) share the same prop vocabulary. Page-specific
components nest under the page's namespace (`Admin::Annotations::*`).
Components call app helpers through `helpers.` (e.g.
`helpers.turbo_frame_tag`). Existing partials stay until they're touched;
each opens with a strict-locals declaration (`<%# locals: (artifact:,
type:) %>`) and uses no instance variables.

## Style

Follow the template's rules: small composable functions named after meaning,
transformations over loops, early returns, no boolean parameters, comments
explain why and never what, prefer duplication to the wrong abstraction.
TypeScript is JavaScript with contracts — no type soup. Run `bin/rubocop -a`
before finishing; `rubocop-rails-omakase` is the base.

## Architecture diagrams

`docs/family-tree-architecture.md` holds Mermaid diagrams of the family-tree
subsystem as it *is* (plans in `docs/*-plan.md` describe where it is going).
A change that adds, removes or re-routes a step in a diagrammed flow updates
the diagram in the same PR, and a new subsystem of comparable size gets its
own `docs/<area>-architecture.md`. Diagrams show mechanism (what calls what,
what data crosses each arrow), not file listings; keep each one to a screen
and prefer two small diagrams over one large one. Reviewers: a diagram that
no longer matches the code is a finding.

## Auth

Devise with database_authenticatable, recoverable, rememberable, validatable.
No registration and no OmniAuth — an administrator creates users in the admin,
and the `admin` boolean (via `User#can_administer?`) gates `/admin`. Seeds
bootstrap the admin account from `ADMIN_EMAIL`/`ADMIN_PASSWORD` (required in
production, defaulted in development).

## Deploy

Home NixOS server (`~/projects/nixos-server`, `apps/personal/family-archive.nix`).
Pushing to `master` runs `.github/workflows/deploy.yml`: build the image to
GHCR, SSH in, `scripts/deploy.sh family-archive <digest>`. Env comes from
sops via that nix file; `DATABASE_URL` points at PgBouncer in transaction
mode, so production `database.yml` disables advisory locks and prepared
statements. The Solid stack (cache/queue/cable) lives in SQLite files under
`storage/` on a Docker volume, not in Postgres; Sidekiq on the server's
Redis is the planned replacement. Active Storage uploads go to S3
(`AWS_*` env vars); `AWS_S3_KEY_PREFIX` (default `production`) namespaces
blob keys under a folder in the bucket. Cutover runbook:
`nixos-server/docs/FAMILY-ARCHIVE-CUTOVER.md`.

## Production data

`bin/pull-prod` replaces `family_archive_development` with a copy of
production: `ssh nix-server` as `deploy`, `sudo -n -u postgres pg_dump`,
then a `pg_restore --list` sanity check, then drop, create and
`pg_restore` inside the compose container (Postgres 17), then
`db:environment:set` and `db:migrate`. The dump at `tmp/prod.dump` is
owner-only; it holds production password hashes. Users come over
as-is, so log in with your production credentials. The restore re-renders
the `chk_role` check constraint, so `db/schema.rb` shows a diff after every
pull; don't commit it. Plan and record: `docs/prod-db-pull-plan.md`.

Production blobs keep `service_name: amazon` and load from S3 through a
read-only IAM user (`docs/aws-dev-access-plan.md`); new dev uploads still go
to `storage/`. Put these in a gitignored `.env`, which foreman (`bin/dev`)
loads:

```sh
AWS_PROFILE=family-archive-dev
AWS_REGION=us-east-2
AWS_S3_BUCKET=marias-family-archive
```

Keys stay in `~/.aws/credentials`: `storage.yml` passes nil keys, so the
SDK falls back to `AWS_PROFILE`. Viewing works. A file prod never made a
thumbnail for shows its original instead (`ArtifactFile#thumbnail?`), and
nothing tries to generate one. Purging a prod blob fails with AccessDenied in
`/admin/jobs` and leaves S3 untouched. `bin/rails console` doesn't read
`.env`, so export the variables there if you need them.

- `test/integration` — public pages, the tree page and its edit forms, admin gating.
- `test/system` — headless Chrome; guards the Vite/Tailwind pipeline and the
